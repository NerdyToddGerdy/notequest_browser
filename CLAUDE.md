# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A browser-based digital adaptation of *NoteQuest* (by Tiago Junges), a solo, dice-driven, pen-and-paper dungeon-crawler board game. Target deployment is GitHub Pages (static hosting, no backend).

`docs/game-rules-reference.md` is the authoritative transcription of the rulebook (Core Book + Expanded World) — treat it as the source of truth for any table, mechanic, or dice logic. Don't invent rules not present there. The purchased rulebook PDF itself is intentionally not tracked in git (see `.gitignore`) since this repo is public.

`design/mockups/*.html` are standalone, self-contained (fonts embedded as base64) interactive layout studies used to validate screen designs before they're built as real components. They are not part of the app build, and are left as-is once ported — don't edit them expecting it to affect the app. Both current mockups (`character-creation.html`, `dungeon-building.html`) have been ported to real code; treat the mockups as historical design reference, not spec-of-record (the real code has since diverged in places, e.g. the dungeon screen's sidebar).

**Scope discipline**: v1 (Core Book rules only — character creation, procedural dungeon crawl, combat, torches/darkness, death/graveyard) is complete. The project has since moved into the Expanded World phase (hexcrawl, cities, politics, warfare, multiplayer, advanced classes) — hexcrawl itself (issue #19) already shipped; the rest, including local multiplayer/Group Play (#29) and networked cross-browser sharing (#6), is all active, in-scope work now (issues #20, #22-30, #6) rather than deferred — pick up whichever is next roughly in the dependency order laid out across those issues, or whichever the user asks for by number, without treating any of them as premature.

## Commands

```
npm run dev       # start the Vite dev server
npm run build     # typecheck (tsc -b) then production build to dist/
npm run preview   # serve the production build locally
npm run lint      # eslint .
npm run format    # prettier --write .
npm run test      # vitest run (single pass)
npm run test:watch
npm run test:e2e  # playwright test -- e2e/, real browser regression tests
```

Run a single test file: `npx vitest run src/engine/__tests__/character.test.ts`.

`e2e/` holds Playwright specs (`playwright.config.ts`, `tsconfig.e2e.json`) — a separate suite from Vitest's `src/**/__tests__/`, added for regressions that only show up end-to-end (localStorage session state → real rendered UI), not reachable by testing pure reducer/engine functions in isolation. `vite.config.ts`'s `test.exclude` keeps Vitest from trying to run these files itself (they use `@playwright/test`'s own `test`/`expect`, not Vitest's). `webServer` in `playwright.config.ts` starts `npm run dev` automatically and reuses an already-running one locally (`reuseExistingServer: !process.env.CI`).

Node 20.17 is installed locally; some newer devDependencies want >=20.19 and npm prints `EBADENGINE` warnings on install. These are warnings only — install/build/test all work — but if a dependency install starts hard-failing, that mismatch is the first thing to check.

## Architecture

**Data-driven engine, not per-screen hardcoding.** Game rules live as typed data in `src/data/` (`races.ts`, `classes.ts`, `spells.ts`, `dungeonTypes.ts` — Segments/Secret Passage/Dungeon Name tables, shared across all 6 dungeon types — and `dungeonTables.ts` — the per-type Trap/Room Content/Monsters tables), keyed by dice-roll value, e.g. `RACE_TABLE[7]` for a 2d6 roll of 7. Pure game logic lives in `src/engine/` and takes an injectable `RNG = () => number` (defaulting to `Math.random`) so tests can pass a seeded generator (`src/test/mulberry32.ts`) for deterministic assertions instead of asserting on ranges. UI components consume `src/engine` functions and never re-implement roll logic themselves.

**Recurring conventions used throughout this codebase** (referenced below by name rather than re-explained each time):
- *Documented, deliberate simplification*: where the rulebook references a system this app doesn't model (hand-economy, per-item inventory pricing, ally-in-combat, day-passage), the effect is resolved as flavor-only text or a flat coin/HP value rather than inventing new infrastructure. Precedents: `bladeTrap`'s roll-of-2 ("loses an arm," no hand-tracking), `WeaponEntry.twoHanded` (tracked, unenforced — no off-hand slot exists), `DUNGEON_TYPE_BY_TERRAIN`'s thematic substitution for the 8 not-yet-built dungeon types.
- *No formal taxonomy, substring/tag matching instead*: monster "categories" (Undead, Vampire, insect/arachnid) and item bonuses against them are matched via case-insensitive substring checks against `MonsterTemplate.name` (`matchesTags()`) rather than a category enum, since the rulebook itself has no such system.
- *Optional field, back-compat default*: new persisted fields on `WorldState`/`AdventurerResources`/`DungeonState` are typed optional and defaulted at the read site (`?? []`/`?? null`) so an old `localStorage` save doesn't crash the app; `session.ts`'s `loadSession()` back-fills as needed.
- *Reducer decides, UI mirrors*: client-side checks (button disabling, `canTravelTo()`, `hasPendingRoomEntry()`) duplicate the reducer's own gating purely for UX responsiveness — the reducer/engine function is always the actual authority.
- *Acquire-once-permanent vs. expires-per-trip*: `advancedClasses`, `animals`, `buildings` persist forever once acquired (mirrors `RESUME_DUNGEON` resetting them for a *new* character, `RETURN_TO_DUNGEON` carrying them over). `hireling` is deliberately different — spent the instant a fresh dungeon trip is entered, matching "you pay to face just one dungeon."
- *Two rulebook entries, one bonus, no double-counting*: where a base Class and an Advanced Class (or a Race and a Hireling) grant the identical effect (Grave Digger/Gravedigger's Undead bonus; Cat-Person/Merchant's sell markup; base-Class Blacksmith/Advanced-Class Blacksmith's repair discount), the check is a single OR'd condition, not two stacking bonuses.

**The dungeon engine** (`src/engine/dungeon.ts`, `dungeonState.ts`, `dungeonReducer.ts`) is the more involved half. A dungeon is a tree of `levels[]`, each holding `segments[]` (rooms/corridors/staircases, positioned in an abstract pixel coordinate space for the map) and `connectors[]`. `dungeon.ts` holds two kinds of pure logic kept separate in the file: (1) *rules* — table rolls, `classifyDoorOpen()` (whether opening a door is an ordinary roll, a staircase descent, the automatic depth-3 Final Room, the "no stairs ever found" dead-end Final Room, or a second staircase reusing an already-discovered level/Final Room); (2) *spatial layout* — `placeChild`'s collision-avoiding placement algorithm, which is **not** a NoteQuest rule, just this project's own way of drawing a coherent map. `dungeonReducer.ts` applies `classifyDoorOpen()`'s result via Immer (`produce`). The reducer's extra `rng` parameter (for silent Room Content/Monsters rolls) means it can't be passed directly to React's `useReducer` — `DungeonScreen.tsx` wraps it in a 2-arg `reduceDungeon`. A second staircase down to an already-discovered level (`reuse-normal`) links straight to that level's own entrance (`segments[0]`) rather than building anything new (issue #54) — same "one shared destination" shape as `reuse-final`; neither rolls or shows up in `bumpStatsForNewSegment`'s tallies (see `DungeonMap`'s `AUTOMATIC_KINDS`).

**Torches and doors**: `DungeonState.torches`/`alive` track the resource that actually matters — every door first rolls the shared `OPEN_DOOR_TABLE` (trap/locked/unlocked) via `RESOLVE_DOOR_LOCK`, *before* `OPEN_DOOR` runs; only "unlocked" (or a resolved lock/trap) proceeds to the Segments-table roll. All torch-spending flows through the reducer's `spendTorches()` helper, which flips `alive` to `false` (the Darkness) instead of going negative. `DungeonMap.tsx`'s door-click handler mirrors the reducer's math client-side purely to decide whether to animate further dice — the reducer is the sole authority on death. Locked doors show "Pick Lock (1 torch) / Break Door (free)"; breaking a door or setting off a trap alerts monsters beyond it. `TrapEntry` carries `torchCost`, `damage` (flat HP, e.g. Acid Spout), `bladeTrap` (roll 1 kills outright, 2 "loses an arm" flavor-only), and `monsters` (an ambush, always noisy). All three trap-firing sites (`RESOLVE_DOOR_LOCK`, `ROLL_SECRET_PASSAGE`, `ROLL_CHEST`'s empty-chest trap) funnel through `resolveTrapOutcome()`, which checks a `trapImmunity` item first before falling through to `applyTrapEffect()`.

**Combat** (`src/engine/combat.ts`) is pure, RNG-injected, exactly like the rest of the engine; `dungeonReducer.ts` is the only thing that mutates `DungeonState.combat`/`hp`/`coins`. `buildSegment()` creates a room, and if `resolveRoomExtras()` rolled a `MonsterTemplate`, `startCombatIfMonsters()` spawns a `CombatState` — except the entrance itself, exempt from Monsters entirely (a deliberate balance call): `resolveRoomExtras()` still rolls the Monsters dice for RNG-consumption parity but discards the result there. `wasNoisy` (a broken door or fired trap) decides whether the monsters get the first attack. Once `state.combat` is non-null, door/passage/level actions all no-op — the only action is `PLAYER_ATTACK`, one full round per dispatch: `resolvePlayerAttack()` resolves the hit (Stoneskin/Intangible/Weakness, plus a roll-of-1 special ability — Explosive short-circuits into an immediate self-destruct bypassing normal damage math), the reducer applies events (Firebreath/Sorcery queue `bonusDamage`, Deathtouch/Paralyze queue onto the monster's own next attack, Regeneration heals immediately, Horde/Necromancy always spawn a fixed extra monster), then `checkUndeadRevival()` on any newly-defeated Undead (skipped if the player holds `ignoresMonsterAbility: "undead"`). `applyMonsterTurn()` closes the round: splits damage into `poisonDamage` (bypasses armor, hits `hp` immediately) and `absorbableDamage` (deferred to `combat.pendingDamage` if the player has usable armor/Hireling, else straight to `hp`), then consumes queued Paralyze/Deathtouch. Paralysis (`combat.paralyzedTurns`) skips the player's next N `PLAYER_ATTACK` dispatches; monsters still act. Victory (`finishIfVictorious()`) rolls `rollLoot()` per Loot-tagged monster killed, credits `coins`, marks the segment `monstersDefeated`, clears `combat`. Hitting 0 HP sets `alive = false`/`deathCause = "combat"` (vs `"darkness"`) and clears `draft.combat = null` at all four death sites — `CombatPanel`'s own `canAct` also checks `hp > 0` directly as a second line of defense. `DungeonScreen.tsx` uses `deathCause` to pick the death message. `handleMonsterDefeat()`'s non-revived-kill branch tallies `killsByName` (lowercased monster name) and `killsByAbility` (one increment per ability) alongside `monsterKills`/`bossKills` — added to unblock Advanced Classes' kill-count requirements (e.g. Ruthless's "10 Imps," Ghostbuster's "10 intangible beings"). Both follow the same lifecycle as `monsterKills`/`bossKills` everywhere. `CharacterSheet`'s "Kills" stat is a `<button>` opening `KillBreakdownModal` (dismiss-only, listing `killsByName` sorted highest-first). `CombatPanel.tsx` rolls the player's weapon die and dispatches `PLAYER_ATTACK` with the raw roll — the reducer applies the modifier/bonus effects. When `combat.pendingDamage` is set, `CombatPanel` renders an absorption chooser (HP / armor piece / Hireling) dispatching `RESOLVE_DAMAGE`; other actions no-op until resolved.

**Screens** live in `src/ui/screens/<ScreenName>/`, one file + one CSS Module each. `App.tsx` holds the only navigation state and switches between `CharacterCreationScreen`, `WorldScreen`, and `DungeonScreen` — there's no router. `TownScreen` isn't in that list: it's a hex-generic component `WorldScreen` renders in place of the map whenever the player is standing on a City/Fortress hex, not a separate top-level screen. Flow is `CharacterCreationScreen` → `WorldScreen` (landing on home, so `TownScreen` shows first) → `DungeonScreen`, with `DungeonScreen` able to send the player back to World (voluntary retreat, alive) or to `CharacterCreationScreen` (death, via `onNewAdventurer` — permanent, no resurrection). **Shared components** in `src/ui/components/`: `Die`/`DicePool`, `CharacterSheet` (a `CreatedCharacter` plus live stats, used in Town/World and the dungeon sidebar), `Equipment`/`Pack` (each takes an optional `onFixArmor`/`onSell` row-action button, used only in `TownScreen`), `Graveyard`, and the dungeon-specific `DungeonMap`/`LevelTabs`/`RoomInspector`/`RollLog`. `src/ui/rollTiming.ts` has the shared `revealDelay()` timing helper.

**The Graveyard** (`src/engine/graveyard.ts`) was the first piece of state to survive a reload; `session.ts` later generalized the pattern to everything else. `loadGraveyard()`/`addGraveyardEntry()` read/write a JSON array under `notequest:graveyard`, both take an injectable `storage: Storage` (same RNG-injection pattern) so tests run in Vitest's Node environment. `DungeonScreen` records an entry in a `useEffect` keyed on `state.alive` flipping false; `CharacterCreationScreen`/`TownScreen` load it once on mount.

**`RecordsPanel`** (`src/ui/components/RecordsPanel/`) is what `CharacterCreationScreen`/`TownScreen` render for the Graveyard — a tab switcher between `Graveyard` and `DungeonsList` (`src/ui/components/DungeonsList/`, fed `dungeonHistory` unfiltered), shown only once *both* have at least one entry; with just one populated, that one renders directly, no tab bar. `DungeonsList`'s status reuses `isDungeonBeaten()`; its unrecovered-remains count uses `countUnlootedRemains()` (sums `remains.names.length` across every segment/level). Clicking an entry never warps/travels to it — its optional "Locate" button (issue #79) only shows where it is on the map.
- `TownScreen` renders it inside a `.recordsCol` beside Adventure in a two-column `.adventureRow` grid (collapsing to one column under 640px), only when `hasRecords`. `Graveyard`/`DungeonsList`/`RecordsPanel` all gained a `compact` prop for this (drops standalone border/shadow/padding, forces the row layout unconditionally via `.rowCompact`). `CharacterCreationScreen`'s usage is untouched (`compact` defaults false).
- **Sorting/locating (#79/#80)**: `dungeonState.ts`'s `sortDungeonsForDisplay()` stably sorts unfinished-before-cleared, preserving whatever secondary order it's handed — `WorldScreen.tsx` pre-sorts by hex-distance from `world.player` (`hexState.ts`'s `findHexForRunId()` + `hexDistance()`); `CharacterCreationScreen` reverses its own raw history for recency. `DungeonsList`'s "Locate" button reuses `findHexForRunId()` then the same `showMap`/`selectedHex` state a direct map click drives.
- **No-Affinity map indicator (#81)**: a hex the character's race has no `hasAffinity()` for gets a dashed `var(--danger)` outline on the hex polygon (all four corners were already claimed by other badges), overridden by the gold `isPlayer`/`isSelected` outlines.

**Session persistence** (`src/engine/session.ts`): `character`, `resources`, `dungeonHistory`, `activeRunId` as one `SessionState` blob under `notequest:session` (same injectable-`storage` pattern). `App.tsx` seeds four `useState` calls from one `loadSession()` on mount, then one `useEffect` re-persists the whole blob on any change. `screen`/`selectedRunId` aren't persisted — a reload resumes wherever `world.player` physically was, or Character Creation if there's no character. `handleNewAdventurer` nulls `character`/`resources`/`activeRunId` (leaving `dungeonHistory` untouched) — the persistence effect handles the rest.

**Settings hard reset** (#50): `session.ts`/`graveyard.ts` export `clearSession()`/`clearGraveyard()` (same injectable-`storage` shape, wrapped in try/catch). `App.tsx`'s `handleHardReset()` calls both, resets every App-owned state field, lands on `screen: "world"` (harmless — `character` is null so the next render falls to Character Creation). Note `clearSession()` only clears what's on disk at that instant — the persistence effect immediately re-writes `notequest:session` with `EMPTY_SESSION`'s shape, which round-trips fine. UI: shared `Footer` component (`src/ui/components/Footer/`), replacing 4 near-identical inline footers — takes `screenLabel` and `onHardReset`, owns its own `ConfirmDialog`-gated "Settings" button. Rendered by all four screens (`WorldScreen` needs it threaded since it renders `TownScreen` in place rather than switching screens).

**Random names** (`src/data/names.ts`, #40): a v1-scoped extra, not a rulebook mechanic. `FIRST_NAME_TABLE`/`LAST_NAME_TABLE` are `Record<RaceName, Record<1-6, string>>` (all 11 races authored) plus a shared `"default"` fallback for races without a table. `rollName()` rolls one die into each table; the "Random Name" button fills the name field directly (no animation), freely editable after. Every New Race falls back to `"default"`.

**New Races** (Expanded World, `docs/game-rules-reference.md` ~1302-1388, #22): three additional 1d6 race tables (`UNCOMMON_RACE_TABLE`/`EXOTIC_RACE_TABLE`/`MONSTROUS_RACE_TABLE`, `src/data/races.ts`) picked instead of the Core Book's 2d6 `RACE_TABLE` — self-contained tables, not modifiers stacked on the base roll. `CharacterCreationScreen.tsx`'s `raceTable` state picks the active table (switching clears any roll already made). `rollRaceFromTable()` is the single entry point — `"core"` delegates to `rollRace()`, everything else a flat 1d6 lookup. A handful of rows re-list a race already in `RACE_TABLE` verbatim and reuse that entry directly. Prohibited Races (a fourth, non-canonical table) is deliberately not offered.
- **Half-Human** resolves entirely at roll time inside `rollRaceFromTable()`: rolling it also rolls Core `rollRace()` and merges that race's `ability`/spell grants onto Half-Human's own name/HP, so downstream code only ever sees one coherent `RaceDef`. The extra roll's dice are appended (`[roll, ...inherited.dice]`) so `DicePool` animates all of them (3 dice: 1d6 table row + 2d6 Core race).
- **Mechanically hooked abilities** (the rest are flavor-only): Patovsky/Sharkin water-walking (`hasWaterWalk()`, `hexTables.ts`); Pandakhan/Centaur travel-cost multiplier (`travelCostMultiplier()`, 2x/0.5x, Centaur rounds up via `Math.ceil`); Ogre's unconditional +2 damage (`attackBonus()`, alongside Grave Digger's Undead-only +2). Pumpkinkin's "3 uses of Vimes" and Corvino's "5 random Advanced Spells" were real data from the moment #24 shipped, now fully functional end-to-end since Vimes became castable (#61). **Samambro**'s death-survival roll (`trySamambroSurvival()`, checked at all seven `draft.alive = false` sites, `rng` now threaded through `spendTorches()`/`applyMonsterTurn()` for it) lets the character survive on 3+ with 1 HP, skipping that site's death bookkeeping on success. **Ogre**'s "cannot use potions, scrolls, or wear armor" is enforced at every grant site — see "Unusable gear is sellable" below for what happens instead. Outside a dungeon, `town.ts`'s `canDrinkVerdosaPotion()`/`canBrewHealthPotion()` take an `isOgre` parameter to disable those buttons. **Goblin**'s "if you roll 1 on the damage die, you explode, dealing 5 damage to everyone in the room" is now real too (issue #60/#67 follow-up): `PLAYER_ATTACK`'s handler checks `raceName === "Goblin" && action.roll === 1` right after resolving the target monster, and if true, entirely replaces the normal single-target hit with a room-wide `resolveSpellDamage(monster, 5)` loop (the identical shape Fireball/Insect Rain/the Hireling Goblin Helper's own `HIRELING_EXPLODE` already use), then still runs the same `finishIfVictorious()`/`applyMonsterTurn()` tail an ordinary attack would (the round is still consumed, surviving monsters still counter-attack). The ambiguity that blocked this ("does it also hurt the Goblin?") was confirmed with the user: monsters only — mirroring Goblin Helper's own explosion, not the Explosive monster ability's player-facing precedent. Fungoid's provision-heal stays flavor-only (provisions aren't tracked inside a dungeon run).
- Deliberately out of scope: per-race starting locations (Orc/Ogre/Exotic races' rulebook-specified alternate starts) — every new race still starts at `world.home` like Core races (see "A new character starts somewhere their race is welcome" below for the one exception that *is* built). `RACE_AFFINITY`'s old combined `"Orc/Ogre"` row was split into separate exact-name rows.

**Unusable gear is sellable instead of vanishing** (#83): every Ogre "cannot use" site rolls the item as normal and sells it via `addHeldItem()` instead of discarding. `resolveMagicItem()`'s armor branch: worth `Math.max(1, base.maxHp)`. `resolveWonder()`: a trinket sells for its own `grantsHp`; a potion/scroll-shaped effect sells for a flat `OGRE_UNUSABLE_TREASURE_WORTH` (3 coins). `applyRoomContentReward()`'s `magicScrolls` bundles the whole roll into one `HeldItem` rather than one per scroll. `OPEN_TREASURE`'s `healAll`/`restoreAllSpells`/`randomSpell` cases get hardcoded item names ("Health Potion"/"Mana Potion"/"Magic Scroll"). `COLLECT_REMAINS` leaves a fallen adventurer's armor behind in the remains rather than force-selling — confirmed as intentional, not a bug.

**Town** isn't a distinct `App.tsx` screen — `TownScreen` is a hex-generic component `WorldScreen` renders in full (map hidden) whenever standing on any City/Fortress hex, home included. `WorldScreen` computes and hands down `hasDungeon`/`dungeonGateCopy`/`onEnterDungeon` for the current hex and `onExploreWorld` (toggles the map view back on). `App.tsx` lifts an `AdventurerResources` object (`src/engine/town.ts` — `torches`/`hp`/`maxHp`/`coins`/`treasures`/`keys`/`heldItems`/`armor`/`weapon`/`spellUses`/`provisions`, everything a living character carries between dungeon and town) alongside `character`; seeded on `onCharacterCreated` (also resets `world.player` to `world.home`, always lands on `screen: "world"`), overwritten wholesale from the dungeon's own fields on `onReturnToTown(runId, dungeon)`. `town.ts`'s `rest()`/`buyTorch()`/`buyProvision()`/`sellItem()`/`fixArmor()` are pure functions `TownScreen` calls, handing the result to `onUpdateResources`; `canRest()`/`canBuyTorch()`/`canBuyProvision()`/`canFixArmor()` gate the buttons (1 coin; torches/provisions capped at 10/20). Selling credits a `HeldItem`'s `worth`; fixing reuses `Equipment`'s `onFixArmor`. `rest()` heals to `resources.maxHp` specifically — this only works because `maxHp` is threaded as its own field everywhere a dungeon is (re)constructed (see `maxHp` note under Resuming, below).

**Resuming an unbeaten dungeon**: dying (or leaving) doesn't erase a dungeon — a later character resumes exactly where it was left. `App.tsx` lifts `dungeonHistory: PendingDungeon[]` (persisted like everything else), keyed by a `runId` (`crypto.randomUUID()`) a `DungeonScreen` instance mints once at mount. Progress is captured generically in an unmount cleanup (reading the latest state via a ref) — fires regardless of *why* the screen unmounts, so `App`'s `handleLeaveDungeon` just drops a run that never went anywhere (`levels.length === 0`), otherwise upserts it — **beaten runs are kept too**, as a historical record only (`isDungeonBeaten()` computed on demand). `App.tsx` separately tracks `activeRunId` — the current living character's own paused run. Choosing what to enter next sets `selectedRunId` and switches screens, driven entirely by `WorldScreen`'s `onEnterDungeon` per the hex the player stands on. From `selectedRunId === activeRunId`, App derives which resume path `DungeonScreen`'s mount-time `useReducer` initializer takes (both land in `restoreMapFromPersisted()` for the shared map-copying/monster-respawn logic, differing in what happens to resources/starting position):
- **`RESUME_DUNGEON`** — a *new* character taking over a *dead* one's map (found by traveling back to its hex). Resets every character-specific field to the new character's own starting `resources`, forces `activeLevel`/`selectedSegId` back to the entrance (`resetToEntrance: true`) regardless of where the previous character died. The dead character's belongings stay as recoverable `remains`, not inherited.
- **`RETURN_TO_DUNGEON`** — the *same living* character returning to their own run's hex. Dispatched automatically on mount when `activeDungeon` is set. Carries over `resources` *exactly* (including coins/treasures/keys/heldItems, which `RESUME_DUNGEON` does not), `resetToEntrance: false`.

Both `structuredClone()` the incoming persisted `DungeonState` (Immer deep-freezes `produce()` output). Either way, an interrupted fight's monsters (at most one such segment dungeon-wide) respawn at full HP via the same `startCombat()` helper. Both also carry an explicit `maxHp` field (as does a plain fresh roll) — `createInitialDungeonState()`'s `startingHp` param historically only set *current* HP, defaulting `maxHp` to match, which broke "retreat below full HP, then come back."

**Remains**: `DungeonState.characterName` labels whose remains they are. `leaveRemains()` in `dungeonReducer.ts` fires at every death site and drops the dying character's coins/treasures/keys/heldItems/armor/weapon onto `SegmentState.remains`, merging if an earlier death already left something. `RoomInspector` shows a free "Recover Remains" button (no roll) dispatching `COLLECT_REMAINS`, crediting the current character and clearing `remains`.

**Hexploring the World**: the rulebook's hex-travel system (`docs/game-rules-reference.md` ~828-1050), built as a deliberately thin first pass — see "still stubbed" list below. `src/engine/hexState.ts` models the map as a sparse `Record<string, HexTile>` keyed by `hexKey({q, r})` (axial, pointy-top), populated 6-at-a-time by `revealNeighborsInPlace()` on entering a new hex. `createInitialWorldState()` fixes the start at `{0,0}`, a human city on a plain, climate hardcoded `"hot"` (`COLD_TERRAIN_TABLE` is authored but unused). `src/engine/hexReducer.ts` is its own small state machine (`MOVE` action), validated against `hexNeighbors()` and `isImpassable()` before mutating `player`/re-revealing neighbors. `WorldScreen.tsx` renders the map as SVG, with City/Fortress/Ruins/Rocks interactive — Portal/Oasis/Volcano/Reef/Thin Ice/"nothing" are inert flavor labels today. `App.tsx`'s `Screen` is `"world" | "dungeon"` (plus gated Character Creation); `world: WorldState | null` persists across characters.

- **Provisions**: parallel to torches but a separate resource. `MAX_PROVISIONS` (20), `canBuyProvision`/`buyProvision` (same 1-coin shape), `payTravelCost()` (spends provisions first; any shortfall costs a flat 1 HP, floored so running out alone can never kill the character).
- **Terrain-based Dungeon Type**: `DUNGEON_TYPE_BY_TERRAIN` (`src/data/hexTables.ts`) maps terrain to a 1d6 table of the 6 built dungeon types, substituting for the rulebook's 8 unbuilt ones (tracked as #30, "Deadly Dungeons"). `App.tsx`'s `onEnterDungeon` rolls the hex's terrain-fated type once, stored as `forcedTypeRoll`; `handleRollDungeon` uses it for just the first of 3 dice.
- **Town Square unification**: `WorldScreen` renders `TownScreen` in full whenever standing on City/Fortress and not voluntarily viewing the map (`showMap`, reset to `false` on every `handleTravel`). `TownScreen` stays hex-agnostic (exception: `cityName`, below): takes `hasDungeon` (true for City/Fortress/Ruins regardless of found-yet, but false once beaten), `dungeonGateCopy`, `onEnterDungeon`, `onExploreWorld`. While voluntarily viewing the map from a city, a "Return to the City" control replaces the map's own Ruins-style "Enter Dungeon" card (reachable only for a genuine Ruins hex).
- **City/Fortress names** (#49): `HexTile.name` (optional, back-compat) fixes "every Human City looked the same" — `rollCityName()` combines two 1d6 rolls from a per-culture `src/data/cityNames.ts` table into a compound word, rolled inside `revealNeighborsInPlace()` atomically with the hex's location. Home is the one exception ("Haven," fixed not rolled). Surfaced in the map hex label, `currentPlaceLabel` (dungeon gate copy prefix, Graveyard "place" field), `HexInspector`'s `cityName` prop, and `TownScreen`'s header (city name as the prominent heading, "Town Square" demoted to an eyebrow).
- **Per-hex dungeon persistence**: `HexTile.dungeonRunId` remembers which `PendingDungeon` was found on a hex — set once on first entry, never cleared. `onEnterDungeon` checks the current tile first; if set, just selects that run (existing `isOwnRun` derivation picks `RETURN_TO_DUNGEON` vs `RESUME_DUNGEON`). On a first visit, the run id is minted in `App.tsx` (`worldFreshRunId`, passed as `externalRunId`) rather than `DungeonScreen` self-minting, since World needs the id up front to stamp the hex immediately. `dungeonGateCopy` comes from `dungeonInfoFor()` (`dungeonHistory` + `isDungeonBeaten()`/`hasUnlootedRemains()`); ⚔/✓ and 💀 map badges render independently. A hex's dungeon, once drawn, stays that hex's dungeon for good — no re-roll action exists.
- **`HexInspector`**: the map's equivalent of `RoomInspector` — a `.hexInspectorOverlay` card describing the selected hex. Clicking a hex travels immediately if it's a valid neighbor; only falls back to selecting-for-inspection (`selectedHex`) otherwise. Every current-tile action lives here now, each combined internally with `isCurrentTile`: "Enter Dungeon" (#59) for a non-City/Fortress hex (`canEnterDungeon`), Train an Animal, Build a Building, Recruit Troop, and — last to move in, #89 — "Return to the City" (`inCityOrFortress`/`onReturnToCity`), previously its own separate `.actionCard` in `WorldScreen.tsx` outside this panel entirely. `inCityOrFortress` and `canEnterDungeon` are mutually exclusive by construction (`WorldScreen` passes `canEnterDungeon && !inCityOrFortress`), so at most one of those two action rows ever renders for a given inspected hex.
- **Map zoom + pan** (`src/ui/hooks/useZoomGesture.ts`): a shared gesture-*detection* hook (wheel + pinch → `onZoom({factor, clientX, clientY})`) used by both `DungeonMap` and `WorldScreen`, applied completely differently by each (`DungeonMap`: CSS `transform: scale()` on `.canvas`, clamped `[0.5, 2.5]`; `WorldScreen`: resizes/repositions the SVG `viewBox`, clamped ~4 hexes to 1.5x natural fit). Both get click-drag panning via `DungeonMap`'s `didDrag` pointer-capture pattern. `useZoomGesture` re-runs its attach effect on every render (not gated on `[ref]`) since `WorldScreen`'s `<svg>` doesn't exist until `showMap` first flips true.

A hex-tied dungeon is resumable **only** by physically traveling back to its hex — no shortcut exists, including for the current character's own active run (an earlier "Continue the Dungeon" shortcut was removed, #44, as contradicting the intended design).

**A new character starts somewhere their race is welcome** (#78): `createInitialWorldState()`'s fixed Human-city `home` is correct for every race except Orc/Ogre (`RACE_AFFINITY`'s only `human: false` rows) — an Orc/Ogre who ever left Haven could never travel back, a guaranteed one-way loss of their starting city. `hexState.ts`'s `findOrRevealCompatibleHome(world, raceName, rng)` (called by `handleCharacterCreated` whenever `!hasAffinity(...)`) searches the already-revealed map first (`findCompatibleCity()`, nearest City/Fortress with matching Affinity), then generates new territory outward ring-by-ring (`MAX_HOME_SEARCH_RINGS = 20` safety cap, falls back to `world.home`). `world.home`'s own meaning is untouched — only *where this one new character gets placed* changes.

**Still stubbed / not yet built** (Hexploring the World): Events on Travel (2d6 wilderness table); Portals (3d6 destination table) and other inert `LocationKind` entry-roll effects (Reef/Oasis/Volcano/Thin Ice); Ruins' own dungeon table and unique outcomes (closer to #30 than #20); the Fortress-Sewers sub-roll (also #30).

**Affinity, Culture Actions, and Hire Boat** (#20 Stage 1, rules ~928-1089): `src/data/affinity.ts`'s `hasAffinity(raceName, location)` implements "Table: Affinity" (14 rows, `DEFAULT_AFFINITY` fallback) — a race with no Affinity can't even travel there (`hexReducer.ts`'s `MOVE`, folded into `WorldScreen.tsx`'s `canTravelTo()`; `HexInspector` explains "You are not welcome here"). Six `town.ts` functions implement one bonus City Action per culture (Human/Dwarf/Elf/Gnome/Goblin/Orc) — mostly flavor-only coin sinks; Elf's Elven Boots is the one real mechanical effect (`hasElvenBoots()`, forest travel drops to 1 provision). `TownScreen.tsx` renders whichever bonus action matches the hex's culture (`cultureActionFor()`). Hire Boat adds `WorldState.hasBoat` (a `HIRE_BOAT` action, must be in a City/Fortress adjacent to water); `isImpassable()` takes it as an optional param; `MOVE` clears it the instant the player lands on non-water terrain.

**"Ask"**: "roll 1d6 ... dungeon appears in that hex; if Water/City/Ruins, go clockwise to the next hex until land with no location." `HexTile.dungeonMarked` is a separate flag from `dungeonRunId` for this — it draws the dungeon on the map before the player has traveled there or a `PendingDungeon` exists (that still only happens once "Enter Dungeon" is later used there). `findAskedDungeonHex()` walks `HEX_DIRECTIONS` clockwise from a rolled side across the current hex's six neighbors; `withDungeonMarked()` mirrors `withDungeonRunId()`. `hexReducer.ts`'s `ASK_FOR_DUNGEON` no-ops outside a City/Fortress or if any neighbor already has `dungeonRunId`/`dungeonMarked`. `canEnterDungeon` and the map-view action card both widened to also accept a `dungeonMarked` hex with no location. `dungeonInfoFor()` gained a fourth status, `"found"` (marked but no run yet), distinct from `"unfinished"` (a run exists) — same ⚔ badge, different copy.

**"Getting Money"** (#58): Hard Work/Gamble/Thug Life live in `town.ts`; Arena gets its own `arena.ts`. Hard Work is City-only (`isFortressLocation()` gates it out, and gates in "Fight in the Arena" instead) — permanently takes 1 HP out of `maxHp` (can never reach 0). Gamble is two sub-games selected by `resources.coins` itself (never a separate action) — `gamble()` returns a `GambleResult` with `outcome: "won"|"lost"|"survivedLifeBet"|"diedLifeBet"`, leaving `resources` untouched on death (App.tsx alone holds the authority to clear the session).

**Thug Life**: `resolveThugLife()` (`town.ts`) — 2d6 City / 3d6 Fortress, returns `ThugLifeResult` with `died`/`banned` flags, mirroring Gamble's death-signaling split. The 5-7 "jail" row can go either way from one follow-up roll (`died: true` if the HP loss would hit 0, else `banned: true`). The ban is **world-scoped**: `WorldState.bannedHexes` (optional, `isBannedHex()`), checked by `MOVE` and `canTravelTo()` the same tier as `isImpassable()`. Resolved once in `WorldScreen.tsx`'s `handleThugLife()` (touches both `resources` and `WorldState`) since `TownScreen` only sees `resources`; the player isn't forcibly evicted on a ban, only blocked from future entry.

**Fighting in the Arena** (Fortress-only): `src/engine/arena.ts` reuses `combat.ts`'s pure `resolvePlayerAttack()`/`resolveMonsterTurn()` directly rather than `dungeonReducer.ts`'s `CombatState` (shaped around segments/loot/armor-choice, none of which Arena has). `ArenaState = { champion; outcome }` — no armor absorption, no spells, no equipped-weapon bonus effect, just the base formula. `resolveArenaRound()`'s one real bugfix: Explosive can defeat the champion *and* kill the player in the same blast — the death check must run **before** the victory check even though `atk.monsterDefeated` is already known. `TownScreen.tsx` owns the fight's UI as local state, un-animated, swapping in for City Actions. Victory credits 20 coins; defeat calls `onCharacterDied("arena", place)`.

**Spellcasting** (`DungeonState.spellUses`, a `Record<string, remainingUses>` seeded by `computeSpellUses()`, keyed by `character.ts`'s composite `spellKey(table, roll)` string, not a bare roll — see New Spells below). Heal/Light are usable anytime (`combat.ts`'s `OUT_OF_COMBAT_SPELL_NAMES` set, matched by spell **name** — see New Spells for why); `town.ts`'s `canCastSpell()`/`castSpell()` mirror the math for Town/World, which have no reducer to dispatch against. Cold Ray/Lightning/Fireball require an active fight, rendered as extra buttons in `CombatPanel`. The "Cast" button always renders for an eligible spell, `disabled` (not omitted) at 0 uses. Spell damage runs through `resolveSpellDamage()` (shares Stoneskin/Intangible filtering with `resolvePlayerAttack()` but never triggers roll-of-1/6 abilities, since it's a fixed value). Casting mid-fight consumes the round like `PLAYER_ATTACK`, except Cold Ray flags `skipNextAttack` and Teleport ends combat immediately. Uses, once spent, stay spent within a run — recovering requires Town's Rest.

**New Spells** (#24): three more 1d6 tables (`NATURE_SPELL_TABLE`, `DEATH_SPELL_TABLE`, `ELEMENTAL_SPELL_TABLE`) plus a 2d6 `ADVANCED_SPELL_TABLE` (`src/data/spells.ts`) — never a free player choice, always *granted* by a race/class/item. Since these reuse 1-6/2-12 roll numbers, every spell-identity site widened to a composite key: `SpellDef`/`FixedSpellGrant` carry `table: SpellTableKey`; anything tracking uses is keyed by `spellKey(table, roll)` (e.g. `"nature:2"`); `parseSpellKey()` is the inverse. `rollSpellFromTable(table, rng)` is the one roll function for all five tables. `computeSpellRequirements()`'s `randomSlotsByTable: Partial<Record<SpellTableKey, number>>` exists because a race and class can grant random spells from *different* tables at once.
- **Why `CAST_SPELL` dispatches by spell name, not `(table, roll)`**: several New Spells rows are the identical Core spell re-listed under a different table (Elemental's Cold Ray/Lightning/Fireball == Basic's) — `combat.ts`'s `KNOWN_CASTABLE_SPELL_NAMES`/`TARGETED_SPELL_NAMES`/`COMBAT_ONLY_SPELL_NAMES`/`OUT_OF_COMBAT_SPELL_NAMES` match against `SpellDef.name` so both copies share one `CAST_SPELL` case. A spell not in `KNOWN_CASTABLE_SPELL_NAMES` simply gets no "Cast" button anywhere.
- **What's mechanically real vs. deferred**: Heal, Light, Teleport, Cold Ray, Lightning, Fireball, plus (issue #61) Natural Cure, Insect Rain, Magic Blast, Banish the Dead, Vimes, Paralyze, Ethereal Body, Magic Shield, Absorb Soul, Fire of the Dead, and Fly all do something real. Everything else (Camouflage, Create Food, Summon Wolf/Skeleton, Awakening, Summon Elemental, Stone Armor, Collapse, Open Portal, Reload Mana) is rolled/tracked/displayed but has no "Cast" button — each blocked on a system this codebase doesn't have (ally-in-combat, temporary armor, the still-stubbed Events on Travel/Portals) or a spell-picker UI.
- **Fly** (Advanced 6, issue #61): "Can move through any land without spending any Provision" — deliberately **not** routed through the shared `CAST_SPELL`/`KNOWN_CASTABLE_SPELL_NAMES` pipeline the way every other real spell above is, since that pipeline's "Cast" button also renders inside a dungeon (via `DungeonScreen`'s `canCastOutOfCombat`), where Fly's effect (Provisions, a World-map-only resource) means nothing — adding it there would need a meaningless dungeon-side `CAST_SPELL` case just to avoid silently consuming a use for no effect. Instead, `town.ts`'s bespoke `canCastFly()`/`castFly()` pair arms a new `AdventurerResources.flyActive: boolean` and spends the use immediately (matching every other spell, which spends on cast regardless of when the effect lands); a "Cast Fly" button/armed-flavor-line lives in `HexInspector` (gated `isCurrentTile`, usable from any hex — Fly is a personal ability, not a place-bound one like Hire Boat). `WorldScreen.tsx`'s `handleTravel()` checks `resources.flyActive` first, before any of the other travel-cost machinery (Elven Boots/Animal overrides, the Mammoth penalty, the Pandakhan/Centaur multiplier, the Hireling surcharge) — a true, unconditional free move, not just the cheapest of several competing overrides — then clears the flag back to `false` once that one move lands. World/Town-only, not mirrored on `DungeonState` (same shape as `travelStats`/`troops`), `loadSession()` back-fills `flyActive ?? false`. The "...and activate Event" half of Fly's text is deferred, same as Camouflage's own Events-on-Travel blocker.
- **Tier 1** (#61): Natural Cure (Nature 1, 12 HP, mirrors Heal, also usable out of combat), Insect Rain (Nature 6/Advanced 2, 7 room-wide, mirrors Fireball), Magic Blast (Advanced 10, 12 single-target, no freeze, mirrors Lightning). **Banish the Dead** (Death 3) is genuinely new: destroys every Undead in the fight outright via `handleMonsterDefeat()`'s `bypassRevival` param.
- **Tier 2** (#61): six spells needing new `CombatState`/`CombatMonsterState` fields, all resolved instantly on cast (round still ends normally). **Vimes** (Nature 2, targeted, 1d6 turns) / **Paralyze** (Advanced 5, room-wide, fixed 2 turns) both set `CombatMonsterState.silencedTurns` (decremented once per round in `applyMonsterTurn()`, skips that monster's damage until it reaches 0). **Ethereal Body** (Death 1/Advanced 12) sets `CombatState.damageReduction` (-1 per hit including poison, applied before the poison/absorbable split — deliberately reduces poison too, reading "all damage" literally). **Magic Shield** (Advanced 8, stackable) pushes onto `CombatState.shields: number[]`, drained oldest-first against `absorbableDamage` before the armor-or-HP choice; poison bypasses it like armor. **Absorb Soul** (Death 2, 5 HP/kill) / **Fire of the Dead** (Death 4, 2 torches/kill) set boolean flags paid out by `finishIfVictorious()` off `combat.engulfableBodies` (Slimemen's existing kill counter, reused rather than tracked twice).
- **Spell uses granted after Character Creation, and the Rest bug** (#75): `CharacterSheet`, `rest()`, and Mana Potion used to compute max uses via `computeSpellUses(character.spells, character.fixedGrants)` — fixed at creation, so any spell granted later (Advanced Classes, Hirelings, Gnome's culture action, Magic Scrolls) never appeared, and worse, `rest()`'s `{...maxSpellUses}` full-replace silently wiped later grants back down every Rest (also silently undoing Anti-Paladin's Heal-zeroing). Fixed with a genuinely persisted `maxSpellUses: Record<string, number>` on both `AdventurerResources`/`DungeonState`, bumped by the same amount at every grant site alongside `spellUses`. `rest()`/`canRest()` now read `resources.maxSpellUses` directly rather than a second passed-in value. `loadSession()` back-fills an old save by taking the *higher* of the creation-time computation or whatever `spellUses` already holds. A related bug fixed in the same pass: `CharacterSheet` always displayed `character.totalHp` (also creation-time) as the max-HP denominator — fixed via a `maxHp` prop (falls back to `character.totalHp`).

**Hirelings actually fight** (#84): the first ally-in-combat concept in this codebase, scoped narrowly (both forks confirmed with the user). `HirelingDef.weaponFormula?: string` is the roll-able version of `equipmentText`, omitted for Hirelings whose text says they can't fight or whose contribution is already a passive player-attack bonus (Minstrel). `CombatState` gains `hireling: {name; hp; maxHp} | null` (a copy, seeded in `startCombat()`) and `hirelingAttackedThisRound: boolean`.
- **A free action that doesn't end the round**: not bundled into `PLAYER_ATTACK`, not a round-consuming alternative. `HIRELING_ATTACK {targetId, roll}` capped once/round by `hirelingAttackedThisRound`, reset at the top of `applyMonsterTurn()` (the one chokepoint every round-ending action already calls). Deliberately **not** gated on the player's own paralysis. Resolution reuses `resolveSpellDamage()` (fixed/rolled value, defense abilities apply, no roll-of-1/6 triggers).
- **A third `RESOLVE_DAMAGE` option**: `hasUsableArmor(draft) || (combat.hireling && combat.hireling.hp > 0)` widens the defer-to-`pendingDamage` check; `absorbWith` widens to include `"hireling"`. A Hireling at 0 HP is gone for good — clears the top-level `hireling` field too.
- `CombatPanel.tsx`: a Hireling HP row, a "`[Name]` Attacks" button per monster, disabled on `!combat.hireling || hp <= 0 || hirelingAttackedThisRound || !weaponFormula` — deliberately not gated on player paralysis.
- Deliberately out of scope: the Arena has no Hireling concept at all.

**The last 9 flavor-only Hireling types** (#63): Torchbearer/Mercenary/Bodyguard/War Veteran/Orc Soldier ("None."), Jester (no clear rule), Elf Ranger (blocked on Events on Travel) stay deferred. Two were unblocked by since-shipped work and built in this same pass:
- **Cargo Ogre** ("carry 40 items") — blocked on there being no Pack cap to raise until #82 shipped `MAX_HELD_ITEMS = 10`. `town.ts`'s `maxHeldItemsFor(hireling, animals)` returns 40 with Cargo Ogre employed — the single chokepoint every cap check goes through. No special "return at the end" handling needed — the cap just reverts when the hire expires.
- **Goblin Helper** ("explode, dealing 5 damage") — blocked on ally-in-combat, unblocked by #84 same day. Confirmed with the user: a genuine one-time detonation (5 damage to every monster, the Hireling destroyed). `HIRELING_EXPLODE` reuses the room-wide damage loop Fireball/Insect Rain established, gated to `combat.hireling?.name === "Goblin Helper"`, free and doesn't end the round, fires only once (self-clears `hireling`). `CombatPanel.tsx` renders one room-wide button, no `weaponFormula`/once-per-round requirement.

**Animals** (#26): 19 companions across Domesticated/Mounts tables (`src/data/animals.ts`, `ANIMAL_BY_NAME`) — trained in the wild, or (Mounts only) bought in a qualifying city. Same "no ally-in-combat" scoping as pre-#84 Hirelings — `hp`/`damage` recorded but unused; every real ability is a travel-cost hook or one dungeon rule. Unlike Hirelings, persists **permanently** once acquired (`AdventurerResources.animals`/`DungeonState.animals: string[]`, `MAX_ANIMALS = 3`), threaded like `advancedClasses`; `loadSession()` back-fills `animals ?? []`.
- **One shared qualification check**: "empty hex, ≥2 same-terrain neighbors" (training) vs. "a city on the right terrain, also with ≥2 same-terrain neighbors" (buying a Mount) — `hexState.ts`'s `countMatchingNeighbors()`/`qualifiesForTraining()`/`qualifiesForBuyingMount()`. Buying a Mount is **culture-agnostic** (only terrain matters). `WorldScreen.tsx` computes both lists for the current hex, passed to `HexInspector` (training) and `TownScreen` (buying).
- **Training spends provisions regardless of outcome**: `trainAnimal()` — pay 4 (8 for a Mount), roll ≥ the animal's Dif to succeed, mirroring Gamble/Thug Life's "pay then roll" shape. Buying a Mount has no roll.
- **13 of 19 have a real ability**: Owl/Giant Wolf/Camel/Raptor/Goat/Llama cap specific terrain provision cost (`animalTravelCostOverride()`, cheapest applicable wins); Griffin's "1 provision anywhere" short-circuits everything else including Elven Boots; Mammoth adds a penalty on top (`animalTravelCostPenalty()`); Dog blocks Move Silently entirely (`RESOLVE_ROOM_ENTRY`'s `"moveSilently"` no-ops if owned, mirrored by `RoomEntryPrompt.tsx`); Horse is approximated as a flat 1-provision Plains cost (not the rulebook's every-other-hex-free); **Raven** (#67) — "If you die, roll a die. If it's 4 or more, you come back" — reuses Samambro's exact death-survival shape (`tryRavenSurvival()`, `dungeonReducer.ts`, checked immediately after `trySamambroSurvival()` at the same 7 `draft.alive = false` sites, so a character with both gets two independent rolls); **Monkey** (#67) — "It can carry an extra item" — `town.ts`'s `maxHeldItemsFor(hireling, animals)` widened to a second parameter, adding a flat +1 on top of whichever base cap applies (stacks with Cargo Ogre's own 40, giving 41 total) rather than replacing it outright.
- **Snake actually fights** (#26/#29/#67): "Attack deals Poison" reuses `HIRELING_ATTACK`'s exact free-action shape (a new `CombatState.animalAttackedThisRound: boolean`, reset alongside `hirelingAttackedThisRound` in `applyMonsterTurn()`) via a new `ANIMAL_ATTACK {targetId}` action, gated on `draft.animals.includes("Snake")`. Unlike a Hireling, deliberately **no** HP/absorption slot for the Snake itself — the rulebook never describes an Animal being harmed or dying in combat, so this is purely a bonus attack, not a second combatant that can be lost (no `RESOLVE_DAMAGE` option, no risk of losing it). "Deals Poison" is read as an ordinary flat hit (poison's rulebook significance is specifically about bypassing the *player's* armor, meaningless when an animal is attacking a monster instead — a documented simplification, same tier as `bladeTrap`'s roll-of-2). Also no `roll` field on the action, unlike `HIRELING_ATTACK` — `AnimalDef.damage` is a flat number (1), not a dice formula, so there's no die to animate. `CombatPanel.tsx` renders a "Snake Attacks" button per monster whenever `isSnakeOwner`, disabled on the same `hp <= 0 || animalAttackedThisRound` shape (no `weaponFormula` check needed). This is also the generalization #29 ("Group Play") flagged as its own remaining scope, applied to the one Animal that actually needed it.
- **Deferred** (#67): Cat/Wolf/Polar Bear ("None."), Tiger (moot, nothing models dungeon-presence to restrict), Eagle (no reveal-more-than-one-ring mechanism), Dolphin (near-moot — no `LocationKind` ever generates on Water).

**Hireling/Animal status lives on `CharacterSheet`, not separate cards** (#77): `DungeonScreen` used to render `Hireling`/`Animals` as extra sidebar cards; `TownScreen` hid Hireling status entirely at a culture with no roster (moot today, every culture has one, but fixed at the root anyway); `WorldScreen`'s map view showed nothing. `CharacterSheet` gained `hireling?: string | null`/`animals?: string[]` props, rendered as extra `<li>` rows in its existing `.abilities` list (resolved via `HIRELING_BY_NAME`/`ANIMAL_BY_NAME` for full detail). `DungeonScreen`'s standalone status cards were removed outright. `TownScreen`'s own actionable `<Hireling roster=...>`/`<Animals buyableMounts=...>` (hiring/buying UI, not pure status) stay as-is.

**Buildings and Politics** (#27, rules 1668-1721): spending coins to build House/Tower/Palace/Castle/City/Fortress on an empty hex (`src/data/buildings.ts`'s `BUILDING_TABLE`), and a Political Affinity roll at any City/Fortress making it an ally, Vassal, or permanent enemy (`src/engine/politics.ts`). Unlocked Noble/Knight/Lord/King/Emperor (previously permanently unbuildable). The item-storage-with-theft mechanic is deliberately deferred — no "storable item" concept exists. **Warfare** (troops/attacking/storming), originally deferred alongside this, is now real too (below).
- **Buildings**: `buildingCost(kind, terrain, raceName)` doubles off-Plains (exempting Dwarf/Mountain, Elf/Forest); `buildingRequirementMet()` gates Palace/Castle on Noble, City on Lord, Fortress on King. Only on an empty hex (`tile.location === null`; a built-on hex still reads "empty" for re-upgrading). Upgrading costs only the difference (`max(0, newCost - oldCost)`, no protection against a 0-cost "downgrade" edge case — documented simplification). `AdventurerResources.buildings: OwnedBuilding[]` mirrored on `DungeonState` (unlike `TravelStats`) since `finishIfVictorious()` reads it mid-dungeon for the tax payout. `src/engine/buildings.ts`'s `canBuildBuilding()`/`buildBuilding()` spend cost, update `resources.buildings`, stamp `world.tiles[hexKey].building` via `withBuilding()`. Surfaced in `HexInspector` as a "Build a Building" list (gated `isCurrentTile && tile.location === null`); a read-only "My Buildings" card in `TownScreen`; a 🏛 map badge.
- **Boss-kill tax**: owning Palace/Castle/City/Fortress credits `buildingTaxTotal(kinds)`'s sum the instant a Boss falls, inside `finishIfVictorious()`'s existing `isBoss` branch.
- **Politics**: `POLITICAL_AFFINITY_TABLE`/`DEFAULT_POLITICAL_AFFINITY`/`politicalAffinityTarget()` (`src/data/affinity.ts`, rules 1706-1720) — a numeric Race×Culture 2d6 target, a genuinely different table from the boolean `RACE_AFFINITY`; races the rulebook's own table omits (Cat-Person/Rinoceroid/Lightbugster) fall back to the default rather than an invented number. `resolvePoliticalAffinity()` rolls at a City/Fortress with no status yet — success is an ally (or Vassal, below), failure a permanent enemy. `WorldState.politicalStatus?: Record<string, "ally"|"vassal"|"enemy">` (optional back-compat), one resolution per hex ever. Resolved in `WorldScreen.tsx`'s `handlePoliticalAffinity()` (touches both `resources` and `WorldState`); surfaced as a "Political Affinity" button in `TownScreen` and a read-only "Politics" row + 🤝/👑/🗡 badge in `HexInspector`.
- **Vassals**: a City (never Fortress) becomes a Vassal instead of a plain ally if the roll succeeds AND the player holds Lord/King AND owns a Castle/City/Fortress within 3 hexes (`hexDistance()`, `parseHexKey()`). King's range is filled in by direct analogy to Lord's rulebook-specified case (documented scoping call). A successful Vassal roll increments `AdvancedClassMilestones.vassalCount`.
- **Noble/Lord/King/Emperor/Knight now trackable**: Noble reads `talkedToKing` (set on any Political Affinity attempt at a Fortress, success or fail — "talking" is the act, not a required success); Lord/King read owned Castle/City; Emperor reads owned Fortress + `vassalCount >= 3`; Knight chains on Noble (which meant widening Paladin's own OR to actually check both branches now that Knight is real). Knight's "Gain a Horse" ability pushes `"Horse"` onto `resources.animals` if there's a free slot and no Mount already owned.

**Warfare** (#28, rules 1722-1763): recruiting troops at owned Castle/City/Fortress or Vassals, marching them (plus optionally the character) to attack a City/Fortress, then choosing to Annex (Vassal) or Loot (razed to Ruins, flat coins) on success. Also "Declared Enemies": every attack rolls a die per other enemy, which can destroy the player's own nearest building. Reuses #27's target Defense numbers and the Political Affinity roll/table directly.
- **Mustering**: `src/engine/warfare.ts`'s `canRecruitTroop()`/`recruitTroop()` — 200 coins at an owned Castle/City/Fortress or a Vassal, capped at one unspent troop per source hex. `AdventurerResources.troops`/`troopSources` are World/Town-only (not on `DungeonState`).
- **Attacking**: `resolveAttack()` always spends *everything* in `resources.troops` at once, plus an optional `joinBattle` toggle (one bonus die; a natural 1 kills the character, but only if the battle is lost). Rolls `troops` d6 (+1 if joining) vs Defense (City 6, Fortress 12).
- **Declared Enemies**: resolved inside the same `resolveAttack()` call regardless of its own outcome — for every `"enemy"` hex (excluding the one just attacked), 1d6, 1-3 sends that many troops against the player's own nearest owned building (tie-broken by lowest Defense); a win destroys it via `withoutBuilding()` (reverts to a plain, re-buildable empty hex, not Ruins). Skipped if the player owns no buildings.
- **Storming**: on a successful attack, `resolveStorming()` offers Annex (re-rolls Political Affinity at +2, success grants Vassal unconditionally, bypassing the peaceful path's Lord/King-within-3 check — "won militarily"; failure auto-falls-through to Loot) or Loot directly (`withRazedToRuins()`, flat coins via `stormingLootPayout()` — 600 City / 1000 Fortress).
- Attacking your own Vassal is blocked (`canAttack()`) — any other City/Fortress is fair game regardless of status.
- **UI**: "Recruit Troop" in `HexInspector` (owned building) and as a `TownScreen` City Action (Vassal hex). "Attack"/"Attack (Join Battle)" as City Action buttons; a won attack swaps the whole City Actions section for the Annex/Loot choice. A `"lost-death"` result calls `onCharacterDied("warfare")`. `attackMessage`/`pendingStorm` are lifted to `WorldScreen` (not `TownScreen`-local) since a winning Loot razes the target to Ruins and unmounts `TownScreen` on the next render before any locally-held message could show.

**Teleport** ("teleport to any empty room") is the one spell whose `CAST_SPELL` action carries extra fields (`destLevel`/`destSegId`) — clicking "Flee — Teleport" in `CombatPanel` swaps the panel for `TeleportPicker`, listing every discovered "empty" room (`isTeleportDestination()` in `dungeon.ts` — a room segment excluding the current combat one, no undefeated/`sneakedPast` monsters, not `needsMonsterReroll` either, since arriving there immediately calls `rerollMonstersIfNeeded()`, which would otherwise spring a fresh fight right after fleeing). Only picking a room dispatches `CAST_SPELL` with that destination; Cancel spends no use. The fled room's `CombatState` doesn't persist — `rerollMonstersIfNeeded()`'s "still waiting" branch resumes it, full HP, if later reselected. `TeleportPicker` also shows a non-interactive "Fleeing from Level X — [Type] (Segment N)" reference line (#56).

**The Boss fight**: each dungeon type's `DUNGEON_TABLES[key].boss` (`Record<1-6, MonsterTemplate>`) is rolled once via `resolveBoss()` in both the `descend-final` and `dead-end-final` cases — no Content/Monsters roll alongside it, only the Boss. Fed through `startCombatIfMonsters()` with a new `isBoss` flag on `CombatState`; `finishIfVictorious()` grants a flat 2d6 Treasures instead of the normal Loot table. `dungeonHistory` is persisted the instant `bossDefeated` flips true via its own `useEffect` (not only on unmount/"Return to Town" click) — a hard reload from the victory screen kills the JS before the unmount cleanup ever runs, and World's beaten-check would otherwise still read the pre-victory snapshot on next load.

**Chests and Loot**: `RoomContentEntry.hasChest` flags Room Content rows describing an actual Chest (vs passive, unapplied flavor text like "1d6 coins on the floor" — see stub list below); a chest can also turn up via a Secret Passage roll of "You have found a hidden Chest!" `RoomInspector` offers a free "Open Chest" action, rolling two dice — higher becomes coins, lower becomes Treasures, unless both are 1 (empty, rolls on the Trap table instead). `DungeonState.treasures`/`keys` are real counters credited by Chests and the Loot monster ability — Keys don't do anything yet.

**Secret Passage → Staircase**: a roll of 6 builds a real, descendable `type: "staircase"` segment via `buildSecretPassageStaircase()` — the door itself is brand new (appended, already `opened: true`), placed in whichever cardinal direction the room doesn't already have a door (only silently no-ops for a fully-4-doored entrance).

**Singular monster names** (#65): `MonsterTemplate.singularName` (only set where `count` could resolve to 1: Goblins, Bats, Skeleton Soldiers, Giant Rats, Scorpions, Cultists, Serpents, Imps) gives `spawnMonsters()` the correct name for a lone survivor. Goblins/Bats/Skeleton Soldiers were consolidated into shared `GOBLINS`/`BATS`/`SKELETON_SOLDIERS_SWARM` constants. `killsByName` genuinely splits "goblin" from "goblins" — Goblinator (`>= 20` Goblins) sums both forms.

**Opening a Treasure**: each dungeon type's `DUNGEON_TABLES[key].treasure` (`Record<1-6, RewardOutcome>`) models the per-dungeon Reward table. Rows redirecting to Wonders/Magic Item/Weapon (`RewardEffect.kind: "rerollColumn"`) resolve a second `rollDie()` into that column. Repeated rows are shared constants (`HEALTH_POTION`, `MAGIC_SCROLL`, etc.). `OPEN_TREASURE` is usable anytime via a die-roll bar whenever `treasures > 0`; mid-combat it consumes the round like `CAST_SPELL`. `restoreAllSpells` (Tomb's Mana Potion) restores to `DungeonState.maxSpellUses` directly. The "worth N Coins in town" outcomes push a `HeldItem` (`{name, worth}`) onto `DungeonState.heldItems` (shown in `Pack`), since there's no town to sell in mid-dungeon.

**Armor & Weapons**: "Table: Armor" (1d6: Ring 0 HP / Bracelets 2 / Boots 3 / Shoulderpads 3 / Helm 4 / Breastplate 10) is one shared `ARMOR_TABLE`; "Table: Weapon" differs per dungeon type. Every Wonder/Magic Item's ability is an `ItemEffect` (`extraHp`/`weaponDamageBonus`/`damageBonusVsTag`/`damageMultiplierVsTag`/`ignoresMonsterAbility`/`trapImmunity`/`doubleChestCoins`/`combatDamageBonus`/`grantsTorches`/`randomSpell`/`lifesteal`/`instantKillOnRoll`/`flavor`) — a small reusable vocabulary; `tags` matching is a case-insensitive substring check against `MonsterTemplate.name`. `MagicItemEntry.fixedFormula` overrides the base-table-then-bonus shape for uniquely-named weapons. `ignoresMonsterAbility` covers two shapes: monster abilities used against the player (`dungeonReducer.ts`'s `ignoresAbility()`) and the player's own attack being defensively blocked (`combat.ts`'s `applyDefensiveAbilities()`, threaded via `resolvePlayerAttack()`'s `ignoreAbilities` array). `trapImmunity` is enforced by `resolveTrapOutcome()` — blocks the whole trap including torch cost, one-shot consumed. `WeaponEntry.twoHanded` remains tracked but unenforced (no hand-economy system).
- **Acquiring items** (`resolveWonder()`/`resolveMagicItem()`, called from `OPEN_TREASURE`'s `rerollColumn`): a Wonder either grants its own HP-bearing item or, with no HP of its own, becomes a `DungeonState.armor` entry at `hp: 0, maxHp: 0` (equipped/visible, never offered as damage-absorption) — except `combatDamageBonus` (Potion of Fury), added directly to `combat.playerDamageBonus` if a fight is active, logged as wasted (not silently discarded under generic success text) if not. A Magic Item is "[Armor] of X" or "[Weapon] of X": rolls the base table for the concrete piece, layers the effect on top (`extraHp` baked into `hp`/`maxHp`, anything else becomes `effect`/`bonusEffect`); a new weapon never overwrites `DungeonState.weapon` directly — pushes onto `spareWeapons` instead.
- **Wearing them**: `DungeonState.armor: ArmorPiece[]`/`weapon: EquippedWeapon | null` (mirrored on `AdventurerResources`/`FallenAdventurer`) thread through every construction site like `heldItems` — `RESUME_DUNGEON` does **not** carry them (becomes remains instead). `Equipment` renders both, read-only in `DungeonScreen`, with a "Fix (1 coin)" button in `TownScreen`.
- **A spare weapons inventory** (#48): `DungeonState.spareWeapons: EquippedWeapon[]` (mirrored as `weapons` on `FallenAdventurer`) — every weapon grant pushes here instead of overwriting `weapon`, since a weapon can appear automatically just from opening a door (no interrupting choice prompt). `WIELD_WEAPON {index}` swaps a spare into `weapon`, pushing the old one back into `spareWeapons`; `town.ts`'s `wieldWeapon()` mirrors it for Town. `Equipment` renders a "Spare Weapons" list with per-row "Wield" buttons in both `DungeonScreen` and `TownScreen`. Selling a spare weapon is out of scope (no price data for weapons).
- **Armor slot uniqueness, spare armor, and a Pack cap** (#82): "can't use more than one identical piece" was never enforced. `addArmorPiece()`/`addArmorPieces()` (`dungeonReducer.ts`) are the single chokepoint replacing all raw `draft.armor.push()` sites — a piece for an already-occupied one of `REAL_ARMOR_SLOTS` (5 real slots; Ring/`wonderItem` are exempt, not slot-unique) benches into `DungeonState.spareArmor` instead. Mirrors `spareWeapons` exactly, plus its own `WIELD_ARMOR {index}`/`wieldArmor()` (has to find-and-displace *that spare's own slot*, not just whatever's currently equipped).
  - **Pack cap**: `town.ts`'s `MAX_HELD_ITEMS = 10`. Exactly two sites push to `heldItems` (`OPEN_TREASURE`'s heldValue cases, `COLLECT_REMAINS`), both check the cap first.
  - **The interactive swap**: `DungeonState.pendingPackItem: HeldItem | null` holds an item that didn't fit. `isActionBlocked(state)` (`hasPendingRoomEntry(state) || pendingPackItem != null`) replaced every `hasPendingRoomEntry()` call site. `OPEN_TREASURE` at a full Pack sets `pendingPackItem` instead of pushing (the Treasure is still spent). `COLLECT_REMAINS` takes as many `heldItems` as fit; overflow becomes `pendingPackItem` (first item) plus a shrunken `seg.remains` (rest), nothing lost. `RESOLVE_PACK_SWAP {discardIndex: number | "decline"}` resolves it and is deliberately exempt from `isActionBlocked` (it's what clears the block). `DISCARD_ITEM {index}` lets a player drop an item anytime (blocked like everything else during a pending swap). `Pack` renders capacity ("N/10"), a free Discard button per row, and an inline swap prompt when `pendingPackItem` is set. Not threaded through `RESUME_DUNGEON`/`RETURN_TO_DUNGEON` (always `null`) — safe since Retreat is gated on `!pendingPackItem`.
- **Taking damage with armor equipped**: the HP-vs-armor choice is genuine, not automatic (see Combat above for the full mechanics: `poisonDamage`/`absorbableDamage` split, `pendingDamage`, `RESOLVE_DAMAGE`).
- **Fighting with a found weapon**: `attackBonus()`/`attackMultiplier()` read `DungeonState.weapon?.bonusEffect` (plus `combat.playerDamageBonus`) — only one bonus effect is ever active on a given weapon at a time.

**Still stubbed / not yet built**: `WeaponEntry.twoHanded` (tracked, unenforced — no off-hand/shield slot exists).

**Move Silently**: a quiet arrival into a room with monsters no longer auto-starts combat — `finishRoomSegment()` only does that for a noisy one. Instead it waits for `RESOLVE_ROOM_ENTRY`: **Attack First** (free, this app's old default outcome) or **Move Silently** (1 torch; one die per monster resolved server-side — any 1 means detected and monsters attack first, otherwise `sneakedPast` and combat never starts). `hasPendingRoomEntry()` blocks every other action until the choice is made. A `sneakedPast` room's monsters wake (`wakeSneakedPastMonsters()`) if a later noisy action happens in that segment; `rerollMonstersIfNeeded()`/`restoreMapFromPersisted()` both treat it as still-occupied. Halfling's "roll two dice, discard the lowest (except Boss)" applies server-side in the same case; Boss rooms never reach `RESOLVE_ROOM_ENTRY` at all. `RoomEntryPrompt` is the UI, rendered in place of `RoomInspector` while pending — both `DungeonScreen.tsx`/`DungeonMap.tsx` also check `state.alive` directly, since dying to that room's monsters never marks `monstersDefeated` and would otherwise reshow the prompt alongside the death panel.

**Race and class abilities**: `DungeonState.raceName`/`className` (plain strings, matched exactly) thread through every dungeon construction site alongside `characterName`, so `dungeonReducer.ts` can gate ability checks without the full `CreatedCharacter`. Client-side-resolvable abilities (`TownScreen`, `RoomInspector`) read `character.race`/`character.cls` directly.
- **Combat**: Grave Digger's +2 checks `monster.abilities.includes("undead")` (an ability, not a name match). Cook's +1 coin (except Undead) and Slimemen's `engulfableBodies` tracking live in `handleMonsterDefeat()`'s non-revived branch. Rinoceroid's horn is a second per-monster `CombatPanel` button (`PLAYER_ATTACK` with `useHorn: true`) — flat 1d6, no modifier, skips equipped-weapon effects, but general combat buffs still apply.
- **Doors/torches**: Locksmith's free lock-picking and Lumberjack's torch-from-breaking-a-door both live in `RESOLVE_DOOR_LOCK`. Miner's "leave the dungeon if out of torches" is a `spendTorches()` special case — the failed action just fails, leaving the character alive at 0 torches to use Retreat to Town normally.
- **Town**: Blacksmith's `fixArmor()` (`isBlacksmith` flag, 1 torch instead of 1 coin); Cat-Person's `sellItem()` (`isCatPerson` flag, doubles coins). Both optional, default `false`.
- **Dwarf** (`RoomInspector.tsx`, client-side): Find Secret Passage rolls two dice, keeps the higher, when `raceName === "Dwarf"`.

**Monster table re-roll on return**: resting in Town (or `RESUME_DUNGEON`) means fresh monsters may occupy any currently-empty room — `restoreMapFromPersisted()` flags every built, empty/cleared room-type segment `needsMonsterReroll` (except a just-respawned interrupted fight, and the entrance, #55 — guaranteed empty and would otherwise reroll into a fight the instant a `RESUME_DUNGEON` character lands). Resolved lazily by `SELECT_SEGMENT` (`rerollMonstersIfNeeded()`) the next time that room is actually viewed — not eagerly, since only one `CombatState` slot exists at a time. Only `monsters`/`monstersDefeated` are touched, not room content/chests/passages.

**Positional movement**: `DungeonState.currentSegId` (where the player physically stands) is distinct from `selectedSegId` (what `RoomInspector` displays) — `SELECT_SEGMENT` keeps them in lockstep, only succeeding for a *reachable* segment. `reachableSegIds()` (`dungeon.ts`) computes the fog-of-war boundary: `currentSegId` plus everything connected by an already-opened door, walked bidirectionally. Segments outside render greyed out and can't be selected; `OPEN_DOOR`/`RESOLVE_DOOR_LOCK` guard `action.segId === state.currentSegId` server-side. `currentSegId` auto-advances the moment a door opens into a new segment. `SWITCH_LEVEL` (an already-opened staircase) also moves the player, validated the same way. A level other than wherever `currentSegId` sits ends up with an empty reachable set as an emergent property — so `LevelTabs` doubles as free, read-only history browsing. `restoreMapFromPersisted()` resets `currentSegId`/`selectedSegId` to `activeLevel`'s entry segment (`segments[0]`) for both resume paths — a walk back is still required, so Monster re-roll can't be silently bypassed. An interrupted fight is the one exception (resumes exactly where it was).

**Room Content rewards**: `RoomContentEntry.reward` (`coins`/`treasures`/`magicScrolls`/`magicItems`, each carrying a `MonsterCount`) flags Room Content rows describing an automatic, mechanically-applied reward. `applyRoomContentReward()` resolves it the moment the room is built: `coins`/`treasures` credit directly (an optional `multiplier`), `magicScrolls` grants that many random Basic Spell uses, `magicItems` rolls that many via `resolveMagicItem()` (two `rollDie()` calls per item — the Magic Item table, then the base Armor/Weapon roll). `finishRoomSegment()` composes this with `startCombatIfMonsters()` at all 4 real room-building sites (reward first, then combat) — the 2 Final-Room/Boss sites are untouched.
